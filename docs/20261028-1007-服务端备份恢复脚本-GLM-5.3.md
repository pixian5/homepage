## 一、新增脚本

| 脚本 | 作用 |
|---|---|
| `scripts/backup-sync-state.sh` | 备份同步状态目录：校验 JSON → tar.gz 打包 → 可选保留份数清理 → 打印恢复命令 |
| `scripts/restore-sync-state.sh` | 恢复：校验归档 → **停服务** → 备份当前状态 → 替换 → 启动 → `/health` 验证 |

两者都支持 `--dry-run`（恢复脚本）与自定义目录参数；`setup-sync-server.sh` 现在会一并安装到 `/opt/homepage-sync/`。

### 设计要点

- **备份前校验 JSON**：服务端是原子写入，但备份脚本仍先用 Python 解析一遍，避免把半损坏文件打进归档；
- **恢复前自动快照**：恢复动作会先把当前状态打包成 `pre-restore-*.tar.gz`，误操作可回退；
- **恢复失败不启动服务**：归档损坏时保持停止状态，不把坏数据暴露给客户端；
- **归档结构校验**：必须含 `homepage-sync-state.json` 且能解析、含 `revision`/`doc`/`state` 之一，防止恢复错误备份；
- **属主修正**：恢复后 `chown -R homepage-sync:homepage-sync`，保持 systemd 服务可写。

## 三、生产云端首次播种（本轮一并完成）

因为本机网络对服务器 IP 的 TLS 被拦（见[部署文档](20261028-0945-生产同步部署oh.sbbz.tech-GLM-5.3.md)），改用服务器侧直接播种：

- 用项目自己的 `toSyncDocument()` 从本机真实数据生成投影，**docId 与本机 `_syncMeta.docId` 一致**（`doc_13d6ed8f…`），避免日后客户端判定 docId 冲突；
- PUT 后 `revision=1`、`deviceId=dev_safari_local_seed` 入设备表、`hasState: true`；
- 回读校验：45 节点、3 分组、43 placements、contentHash `ad05b3d7`，与本机投影完全一致。

**副产品**：服务端自动记录了 4 条删除版本（`deletions`）并算出 `reclaimCandidates`——墓碑回收机制第二次阶段在生产环境首次真实跑通（仍为只诊断、未回收）。

> 注意：播种用的 `dev_safari_local_seed` 是临时设备 ID。本机扩展真正同步时会生成/使用自己的 deviceId 并入表；那条 seed 记录会留在设备表里，可在设备退役功能落地后清理。

## 四、运维命令速查

```bash
# 手动备份（服务器上）
sudo /opt/homepage-sync/backup-sync-state.sh --keep 14

# 查看有哪些备份
ls -lh /var/backups/homepage-sync/

# 恢复到指定备份
sudo /opt/homepage-sync/restore-sync-state.sh \
  --archive /var/backups/homepage-sync/homepage-sync-20261028T100739Z.tar.gz

# 先演练不改动
sudo /opt/homepage-sync/restore-sync-state.sh --archive <file> --dry-run

# 拉回本机
scp root@oh.sbbz.tech:/var/backups/homepage-sync/*.tar.gz ./
```
