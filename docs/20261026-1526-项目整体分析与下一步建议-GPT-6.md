### 1.3 明显的结构性风险

| 风险 | 现状 | 影响 |
|---|---|---|
| `app.js` 单文件过大 | 4,813 行，设置/导入导出约 771 行、拖拽约 561 行、渲染约 342 行 | 改动易互相牵连，回归成本高 |

## 二、必须先处理的紧急问题（本轮实测发现）

### 2.1 生产同步已经中断约两个月

从本机 Safari 实际数据读出：

| 指标 | 值 |
|---|---|
| 最后一次成功推送 | **2026-08-27 18:29** |
| 最后一次成功拉取 | 2026-09-05 00:45 |
| 当前状态 | `error` / `network_error` |
| outbox | 1 条，**attempts = 12（已达上限）** |
| 本地最后修改 | 2026-10-25 00:22 |

也就是说：**近两个月的本地改动完全没有上云，且重试已经放弃**。

### 2.2 生产同步服务当前不可达

```
curl https://sf.sbbz.tech:58443/health
→ TLS connect error: unexpected eof while reading
dig sf.sbbz.tech → 198.18.30.34
```

`198.18.0.0/15` 是代理软件的保留网段，说明域名被本机代理接管，
真实服务器是否存活尚未确认。端口 58443 可连通，但 TLS 握手被对端直接断开。

**这条不解决，后面所有同步相关工作都没有意义。**

### 2.3 建议的处理顺序

1. 先确认服务器是否存活（SSH 上服务器看 `systemctl status homepage-sync`、`journalctl`）。
2. 若服务已停：修复后**先扩容服务端备份**，再让客户端重试。
3. 若只是 DNS/代理问题：给客户端加「直连」或「自定义 DNS」说明，避免再次误判。
4. 服务恢复后，在 Safari 里手动「立即同步」一次，确认 outbox 能清空。

> 注意：outbox 已达 12 次上限，服务恢复后 `flushOutbox` 会直接返回 `outbox_exhausted`。
> 需要手动同步（`pushNow`）才会重新尝试；这一点应写进用户文档，或改成「手动同步重置 attempts」。

## 三、按优先级排列的开发建议

### P0：同步可靠性（1～2 天）

**P0-1 手动同步重置 outbox 退避**
- 现状：`flushOutbox` 在 `attempts >= 12` 时直接失败；`pushNow` 不重置 attempts。
- 建议：手动同步前把 outbox 的 `nextRetryAtMs` 清零、`attempts` 保留但允许强制一次。
- 收益：用户点「立即同步」就能自救，不用清数据。

**P0-2 同步状态跨标签页同步**
- 现状：`attachStorageListener` 只监听 `homepage_data`，不监听 `homepage_sync_state`。
- 建议：同时监听状态键，变化时调用 `refreshSyncStatusLine()` 并更新冲突按钮。
- 收益：多标签页下状态一致，减少误判「冲突已解决/未解决」。

**P0-3 同步失败的可见提示**
- 现状：后台推送失败只写存储，用户看不到；outbox 耗尽也没有提示。
- 建议：连续失败 N 次后在新标签页顶部显示一条可关闭的提示条，带「立即重试」与「查看设置」。
- 收益：像本轮这种「两个月没同步」的情况能被用户及时发现。

### P1：服务端可运维性（2～3 天）

**P1-1 服务端状态备份与恢复脚本**
- 现状：`/var/lib/homepage-sync/...json` 只有原子写入，没有定时备份与恢复流程。
- 建议：新增 `scripts/backup-sync-state.sh`（tar + 保留 N 份）与 `scripts/restore-sync-state.sh`
  （先停服务、校验 JSON、再启动），并在部署工作流里加「部署前备份」。
- 收益：墓碑回收、服务端升级前都有退路。

**P1-2 健康检查增强**
- 现状：`/health` 只返回 `ok / hasState / authRequired`。
- 建议：追加 `revision`、`updatedAt`、`lastWriteOk`、`docBytes`，便于判断「服务活着但数据停滞」。
- 收益：能区分「服务挂了」和「客户端没在推」。

**P1-3 CI 加入 Firefox 冒烟**
- 现状：CI 只跑 Chrome（`test:browser-smoke -- chrome`）。
- 建议：在 CI 安装 Firefox ESR 或无头 Firefox，跑 `-- firefox`；Safari 继续留本机。
- 收益：本轮修掉的 Firefox 专属问题（事件类型、会话恢复）能被自动发现。

### P2：代码结构（3～5 天，可分多次）

**P2-1 拆出设置控制器**
- 目标：把 `app.js` 第 ~2680–3450 行（设置面板 + 同步设置 + 导入导出入口）抽成
  `settings-controller.js`，通过显式传入 `{ getData, setData, persist, render }` 连接。
- 预计减少 `app.js` 约 700 行，且设置相关回归可单独跑。

**P2-2 拆出拖拽控制器**
- 目标：第 ~1370–1930 行（触摸拖拽、右键菜单、放置计算）抽成 `drag-controller.js`。
- 注意：这部分与 DOM 结构强耦合，建议先补一组「拖拽结果」纯函数测试再搬。

**P2-3 拆分后的约束**
- 每次只拆一个控制器，拆完立即跑：`npm test`、`npm run check`、Chrome+Firefox 冒烟。
- 同步更新 `scripts/firefox-modules.json`，否则 Firefox 打包会缺模块。

### P3：缓存与配额（1～2 天）

**P3-1 图标缓存瘦身**
- 现状：500 条上限、单条 2 KB，实测 756 KB。很多条目来自已删除书签。
- 建议：书签删除时同步移除对应缓存；启动时按「当前书签 URL 集合」清理孤儿条目。
- 收益：预计可降到 300 KB 以内，给数据和备份留空间。

**P3-2 背景缓存改为单张**
- 现状：缓存里保留多天壁纸，实测 432 KB。
- 建议：只保留当天与前一天两张，其余清理。

### P4：功能体验（按需）

**P4-1 同步冲突界面更具体**
- 现状：弹窗只显示 local/remote 的 docId。
- 建议：显示两侧节点数、最后修改时间、差异数量，让用户能判断该选哪个。

**P4-2 周期同步的后台行为**
- 现状：页面 `hidden` 时跳过 tick；自动化里只能覆写可见性验证。
- 建议：补一条真实浏览器「切到后台 1 分钟」的人工验收清单，写进文档。

### P5：长期（需你决策）

**P5-1 墓碑安全回收**
- 现状：永久保留，`SYNC_TOMBSTONE_TTL_MS = Infinity`。
- 现有方案文档（[下一步待实现](20261006-1023-下一步待实现-GPT-6.md)）已经写得很完整：
  设备登记、持久确认、压缩代际、显式退役。
- 建议：**先做 P0/P1，再做这个**。它依赖服务端设备表，且回滚成本高。

**P5-2 独立设备凭据**
- 现状：所有设备共享一个 Token。
- 建议：等设备登记落地后再引入，避免同时改两套协议。
