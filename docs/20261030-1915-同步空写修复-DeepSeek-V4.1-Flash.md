# 修复同步「内容没变也推新版本」的循环（2026-10-30 19:15）

## 现象（源自上一轮排查）

服务端 revision 16:55 = 51，17:27 = 75，期间几乎没有用户编辑。
多设备下形成「拉取 → 落盘 → 再推送」循环：每台设备打开页面都会把同样的内容再写一遍，
版本号无意义增长，其它设备下次加载必然判「有较新数据」。

上一轮只压住了提示（30 分钟限频），根因没动。这次动根因。

## 难点：跨设备哈希不可直接比

`contentHash = hashSyncDocument(doc)` 覆盖整份文档，**包含 `deviceId` / `revision` / `writtenAt`**。
两台设备算出来天然不同，所以不能直接拿本地哈希比远端哈希。

## 做法：用远端的三个身份字段重建本地文档

```js
export function isContentEqualToRemote(data, remoteDoc, docId) {
  if (!remoteDoc?.contentHash) return false;
  const writtenAt = Number(remoteDoc.writtenAt);
  if (!writtenAt) return false;
  const localDoc = toSyncDocument(data, {
    deviceId: remoteDoc.deviceId,       // 用远端的
    docId: docId || remoteDoc.docId,
    revision: Number(remoteDoc.revision) || 0,  // 用远端的
    writtenAt,                          // 用远端的（也决定墓碑过期边界）
  });
  return localDoc.contentHash === remoteDoc.contentHash;
}
```

身份字段对齐后，哈希只剩内容差异——内容一致才会相等。
`writtenAt` 同时是墓碑过期的截止点，必须用远端值才能复现远端那份文档。

## 接入点

`pushNowImpl()` 在读完远端、处理完 docId 冲突和预拉取之后：

```js
if (latestRemote?.doc && isContentEqualToRemote(_getData(), latestRemote.doc, _status.docId)) {
  const pending = await readOutboxItems();
  if (!pending.length) {
    // 不写新版本，只把状态归位
    _status.status = "idle";
    _status.lastError = "";
    _status.lastRemoteRevision = Number(latestRemote.doc.revision) || baseRevision;
    if (latestRemote.etag) _status.lastRemoteEtag = latestRemote.etag;
    await saveState();
    return { ok: true, skipped: true, reason: "unchanged" };
  }
}
```

三个安全边界：

1. **outbox 非空一定推**——队列里就是「上次没发出去的本地改动」，不能因为哈希相等就吞掉。
2. **拿不到 `contentHash` 或 `writtenAt` 时返回 false**（保守推送），避免旧服务端/残缺文档被误判。
3. 跳过时把 `lastRemoteRevision` / `lastRemoteEtag` 对齐远端，后续判断不会误以为本地落后。

## 没有动的地方

`reloadFromStorage()` 仍会在同步开启时调用 `schedulePush()`。现在它退化成
「一次 GET + 本地哈希比较」，不会写服务端。留着是刻意的：逻辑简单、行为可预期，
不像「只在 lastUpdated 推进时才 push」那样容易漏掉真实改动。
