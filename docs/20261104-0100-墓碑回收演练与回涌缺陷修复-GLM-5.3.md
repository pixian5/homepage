## 二、演练发现：协议级缺陷「墓碑回涌」

**现象**：回收后客户端再次同步，服务端 `deletions` 又出现同样 4 条（记录为 revision 115）、文档节点从 43 回到 45、**回收候选全部回来**——回收被完全抵消，且会无限循环（回收→回涌→回收→…）。

**机制**：客户端本地 `data.nodes` 仍持有带 `deletedAt` 的墓碑节点。拉取新基线合并时，合并器把「远端没有」解释为「远端不知道本地删过」，于是保留墓碑——这在正常场景是正确的防复活逻辑，但在 **epoch 回收后**，「远端没有」的真实语义是「已被回收，应丢弃」。随后客户端整包推送，服务端 `collectNewDeletions` 把这些墓碑**再次记为新删除**。

**修复（服务端防御，方案 B）**：新增 `reclaimedIds` 集合（上限 1000）：

1. 回收执行时把本次候选并入 `reclaimedIds`；
2. `collectNewDeletions` 跳过其中的 ID——旧客户端重推已回收墓碑时，推送被接受（兼容）但**不再记为新删除、不再产生候选**，循环被打断；
3. 状态文件落盘该字段，旧状态文件缺失时按空数组兼容。

**二次漏洞（我修复时引入又被自己抓到）**：PUT 分支的 `nextState` 最初漏带 `reclaimedIds`，导致回收写入后**任何一次推送落盘都会把防御集合抹空**（当次内存有效、落盘即失）。真实环境实测发现后已补，并加了专门测试用例锁死（「PUT 落盘必须保留 reclaimedIds」）。

**已知残留（非缺陷）**：已回收墓碑仍可能作为「文档中的普通节点」被旧客户端带回文档（不再进 deletions、不再成候选），属无害冗余，待客户端方案 A 落地后自然消失。

**遗留（下一步，方案 A）**：客户端在拉取发现 epoch 前进时，应主动丢弃本地已不在新基线中的墓碑，从根上不再回推。涉及 `sync_merge` / `sync_engine`，需单独一轮实现。

### 测试

`tests/sync-reclaim.test.js` 新增「墓碑回涌防御」用例：建基线 → 删除 → 确认 → 真回收 → **模拟旧客户端重推含墓碑整包** → 断言 deletions 不回涌、候选为空、PUT 落盘保留 reclaimedIds。

**变异验证**：删掉 `if (reclaimed.has(id)) return;` 防御行 → 测试精确失败于「已回收墓碑重推不得再次进入 deletions」；恢复后通过。

## 三、备份脚本在 macOS 上跑不通（26.2.6 遗留，已修）

演练按流程先备份，`backup-sync-state.sh` 在 macOS 直接报错。两个坑都源于 **macOS 自带 bash 3.2**（此前只在 Linux 服务器上测过）：

1. `line 70: ARCHIVE: unbound variable`——bash 3.2 解析双引号内 `$VAR` 后紧跟多字节字符（如全角括号）时，会把高位字节**并入变量名**。修复：变量一律 `${}` 包裹；
2. `mapfile: command not found`——mapfile 是 bash 4+ 内建。修复：改 `while IFS= read` 循环（POSIX 兼容）。

修复后 macOS 完整跑通：JSON 校验 → tar 打包 → 归档校验 → 列出备份 → 打印恢复命令。`restore-sync-state.sh` 检查无恙。

## 四、演练期间的一起事故与恢复（如实记录）

排查回涌时，我写了一个一次性 Node 调试脚本（临时端口 + 临时数据目录）模拟旧客户端，但其推送**实际打进了真实 8787 服务器**（隔离失效的机制未能完全确证：脚本指向临时端口，但观测到的 revision 序列与真实服务器吻合），把云端文档覆盖成只剩 1 个测试节点，导致客户端进入 `doc_conflict` 冲突态。

**恢复**：本地数据全程完好（45 节点、页面 33 卡片正常）；通过 `resolveDocConflict("local")`（本机覆盖云端）一键恢复——云端回到 45 节点、docId 还原、客户端 idle、无冲突弹窗。恢复后云端 revision 121、epoch 2。

**教训**：
- 一次性调试脚本**必须**用项目现成的 `tests` 基建（随机端口 + 健康检查确认进程真活着再发请求），不要手搓残缺版；
- 对真实数据源操作前，先做一次备份（本轮正是靠演练流程中的备份兜底）；
- 事故 30 秒内发现并恢复，全程向用户如实报告。
