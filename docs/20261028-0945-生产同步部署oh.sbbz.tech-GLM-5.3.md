## 二、部署过程要点（可复现）

```bash
# 1) 客户端配置事实：Token 沿用旧值 "9"，其他设备只需改地址
# 2) 上传服务端与部署脚本
scp -i ~/ed25519 scripts/sync-server.mjs scripts/setup-sync-server.sh root@oh.sbbz.tech:/root/homepage-deploy/scripts/
# 3) 部署（安装 Node 22 → 建系统用户 → systemd 单元 → 启动）
ssh root@oh.sbbz.tech 'cd /root/homepage-deploy && bash scripts/setup-sync-server.sh --token 9'
# 4) nginx 只监听 58443（该机 80/443 已被其它业务占用，绝不能改）
#    配置文件：/etc/nginx/conf.d/homepage-sync.conf
#    并删除 sites-enabled/default，避免抢 80
# 5) 证书复用服务器上已有的 acme.sh 证书（oh.sbbz.tech_ecc，9 月签发）
acme.sh --install-cert -d oh.sbbz.tech \
  --fullchain-file /etc/nginx/ssl/oh.sbbz.tech.fullchain.cer \
  --key-file /etc/nginx/ssl/oh.sbbz.tech.key \
  --reloadcmd "systemctl reload nginx"
systemctl restart nginx
```

### 这台机器的注意事项（重要）

- **80 / 443 已被其它项目占用**（进程 `xbz` / `bz`），部署时绝不能动这两个端口，也不能改默认站点配置去抢 80；
- 因此同步服务固定走 **58443**，与旧服务器端口一致，客户端迁移时不用改端口；
- AWS 安全组已对 80/443/58443 放行（外部节点实测握手成功，`ufw` 本身不活动）；
- 服务器上 `/opt` 还有 `gayme-deploy`、`linuxrecord`、`neon-monitor` 等其它项目，**不要动**。

## 三、本机（Mac）遇到的环境问题：网关代理无差别掐断该 IP 的 TLS

部署完成后，本机 Safari 无法连接新服务器，排查结论如下（这**不是部署问题**）：

| 探测（本机 → 18.191.80.90） | 结果 |
|---|---|
| SSH 22 端口 | ✅ 通（可登录、跑命令） |
| HTTPS 58443（`--resolve` 直连真实 IP） | ❌ `unexpected eof while reading` |
| HTTPS 58443 换任意 SNI | ❌ 同样 EOF（说明不是按域名拦） |
| HTTPS 443（该机其它业务） | ❌ 同样 EOF（说明不是按端口拦） |
| 第三方节点访问 `https://oh.sbbz.tech:58443/health` | ✅ 200 |

即：**本机所在网络（代理网关）对该 IP 的所有 TLS 流量一律中断，仅放行 22**。此前 `sf.sbbz.tech`、`aws.sbbz.tech` 也是同一症状，可判定为本机网络环境的既有问题，而非服务器或代码缺陷。

绕过方式（本次实际使用过、已验证思路可行）：借 SSH 22 建本地转发隧道 `ssh -L 18443:127.0.0.1:8787`，把客户端地址临时指向 `http://127.0.0.1:18443` 完成首次同步播种，再把地址切回正式 HTTPS。隧道在排查结束时已关闭，**客户端地址已切回 `https://oh.sbbz.tech:58443`**。

### 本机客户端现状

| 项 | 值 |
|---|---|
| `settings.syncServerUrl` | `https://oh.sbbz.tech:58443` |
| `settings.syncServerToken` | `9`（与服务端一致） |
| `settings.syncInterval` | `5m` |
| 共享数据 | 45 节点 / 1 分组 / schema 2，完整 |
| 部署前备份 | `~/Library/Application Support/我的首页/homepage-data.json.bak-20261028-部署oh前备份` |

### 附带发现：Safari 扩展 UUID 每次重装都会变

重装 `.app` 后 Safari 记录的 `HomePage` 仍指向旧 UUID（`C71F0FAC…`），而 `pluginkit` 报告新 UUID（`79D9E8C0…`），导致直接打开扩展 URL 报「打开页面失败」。实际新开标签页时 Safari 又会分配第三个 UUID（`ADE19CF7…`）。**手动改写 `HomePage` 无效**（会被重新分配覆盖），排查期间改动的 Safari 偏好已从备份恢复。建议后续把「重装后 UUID 变化」补进 `Safari扩展消失根因` 文档的排查清单。
