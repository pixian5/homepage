# 生产同步服务器整机失联（2026-10-28 17:17）

版本：26.3.8（本轮无代码改动，纯排查）。承接[生产同步部署](20261028-0945-生产同步部署oh.sbbz.tech-GLM-5.3.md)。

---

## 一、现象

用户报告新标签页出现同步失败提示条：

> 同步已多次失败，自动重试已停止。请点「立即重试」，或检查同步设置里的服务器地址。

提示条工作正常——它如实反映了真实故障。

## 二、排查证据链

| 探测项 | 结果 | 说明 |
|---|---|---|
| 系统 DNS `dig oh.sbbz.tech` | `18.191.80.90` | 解析正常，域名没问题 |
| Cloudflare DoH | `18.191.80.90` | 与系统 DNS 一致，无劫持 |
| 本机 `ping 18.191.80.90` | **100% 丢包**（3/3） | 整机无 ICMP 响应 |
| 本机 TCP 各端口 | 22/2424/58443/80/443 均显示「通」 | **假象**：本地代理 TUN 的假握手 |
| 本机 SSH 握手 | `kex_exchange_identification: Connection closed` | 协议层被对端断开 |
| 本机 HTTPS 58443 | `unexpected eof while reading`（读 0 字节） | TLS 层无响应 |
| check-host ping（德国/伊朗） | **TIMEOUT** | 全球节点均不可达 |
| check-host HTTP 58443（巴西/波兰） | **Connection timed out** | 同步服务不可达 |
| check-host HTTP 443（意大利/英国） | **Connection timed out** | **该机上的其它项目也挂了** |
| 扩展自身记录 | `status: error`、`lastError: network_error` | 客户端如实上报 |

### 关键判据

**443 端口上运行的其它业务（`xbz` 进程）同样不可达** —— 这排除了「同步服务被单独打挂」「nginx 配置错误」这类局部原因，指向**整机失联**（EC2 实例停止/宕机/安全组被整体关闭/网络故障）。

对比历史：部署当天（10-28 上午）外部节点访问 `https://oh.sbbz.tech:58443/health` 返回 **200**，现在是 timeout。中间没有任何代码或配置变更。

## 三、结论

| 项 | 判断 |
|---|---|
| 提示条 | ✅ 工作正常，如实报警 |
| 客户端配置 | ✅ 地址与 Token 正确（`https://oh.sbbz.tech:58443` / `9`） |
| 客户端数据 | ✅ 本地 45 节点完好，改动安全排队在 outbox |
| **服务器** | ❌ **整机失联**，含其上所有服务 |
| 数据 | 云端状态最后一次成功备份在 `/var/backups/homepage-sync/`（每日 3:17 自动），若实例可恢复则数据在；若实例销毁则云端数据丢失，但**各客户端本地副本完整** |

## 四、需要用户处理

服务器在 AWS EC2（`18.191.80.90`，俄亥俄），**需要登录 AWS 控制台确认实例状态**：

1. EC2 控制台查看实例是否处于 `stopped` / `terminated`，或状态检查失败；
2. 若实例 stopped → 启动后等 1～2 分钟，`systemctl status homepage-sync` 与 `nginx` 应自动恢复（都已 `enable` 开机自启）；
3. 若实例 terminated → 需重建实例，用 `scripts/setup-sync-server.sh` 重新部署（脚本会一并安装备份/恢复脚本），再从 `/var/backups` 或客户端重新播种；
4. 若实例 running 但网络不通 → 检查安全组规则是否被改动、是否有网络 ACL。

恢复后，各端**点一次「立即重试」**即可：`pushNow` 不受 outbox attempts 上限限制，成功即清空队列。

## 五、给用户的建议

- 这台机器同时跑着其它项目（80/443），整机失联会影响全部服务，建议确认是否有到期/欠费/配额问题；
- 长期看，生产同步更适合放在**独立的小实例**上，避免与其它项目共享同一台机器的可用性风险；
- 客户端侧的提示条已能主动报警，不会再出现「断链两个月无人察觉」的情况——这次从故障到发现是**几小时内**。
