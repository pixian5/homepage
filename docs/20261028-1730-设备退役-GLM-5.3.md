# 设备退役（2026-10-28 17:30）

版本：26.3.9 → **26.4.0**。对应[复核与下一步开发方案](20261028-0832-复核与下一步开发方案-GLM-5.3.md)第 7 步的前半部分。

**要解决的问题**：设备表只增不减。一台废弃/重装的设备会永久留在表里，而墓碑回收要求「所有有效设备都已确认」——这台设备永远不来确认，回收就永远卡住。

---

## 一、实现

### 1.1 设备字段：`retiredAt`

设备表新增退役时间戳（0 = 未退役）。旧状态文件缺该字段时按 0 补齐，兼容现有数据。

### 1.2 新端点 `POST /v1/sync/devices/retire`

```bash
# 退役
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"deviceId":"dev_xxx"}' https://<server>/v1/sync/devices/retire

# 复职（误操作可恢复）
curl -X POST ... -d '{"deviceId":"dev_xxx","retired":false}' ...
```

| 情形 | 响应 |
|---|---|
| 正常退役/复职 | 200，返回 `retired` 与最新 `reclaimCandidates` |
| 设备不存在 | 404 `device_not_found` |
| deviceId 为空 | 400 `invalid_device_id` |
| 未带 Token | 401（管理操作必须鉴权） |

### 1.3 三处行为变更

| 位置 | 行为 |
|---|---|
| `PUT /v1/sync/state` | 退役设备推送 → **403 `device_retired`** |
| `POST /v1/sync/confirm` | 退役设备确认 → **403 `device_retired`**（否则它的确认会让墓碑被误判为「全员已确认」） |
| `computeReclaimCandidates` | **排除退役设备**，不再等待它的确认 |

用 403 而不是 401，让客户端能区分「令牌错误」与「设备已被移除」。

---

## 二、测试

`tests/sync-device-retire.test.js`，3 条端到端用例（真实启动 `sync-server.mjs`）：

1. **完整生命周期**：两台设备登记 → 退役 dev_b → 写入被 403 拦 → 确认被 403 拦 → dev_a 仍正常 → 复职后 dev_b 恢复写入；
2. **边界与鉴权**：未知设备 404、空 deviceId 400、无 Token 401；
3. **回收联动**：dev_b 未确认删除时无候选 → 退役 dev_b 后删除立即进入候选。

### 变异验证

把 `computeReclaimCandidates` 里的退役排除去掉后重跑，第 3 条**精确失败**：

```
AssertionError: 退役设备被排除后，删除应进入可回收候选
```

证明测试真的在守护这条逻辑，不是碰巧通过。

全量测试 **250/250**、Biome 83 文件零警告。

## 三、尚未做的部分

| 项 | 状态 |
|---|---|
| 客户端 UI 暴露退役操作 | ⏳ 未做（当前只能 curl 调用） |
| 独立设备凭据 | ⏳ 未做。目前所有设备共享一个 Token，退役设备只要改 deviceId 就能重新写入——**这是已知的安全边界** |
| 生产环境实际使用 | ⏳ 未做。服务器当前整机失联（见[整机失联排查](20261028-1717-生产同步服务器整机失联排查-GLM-5.3.md)），只能本地验证 |

独立凭据是设备退役真正生效的前提：没有它，退役更像是「礼貌性标记」而非强制约束。但引入设备级凭据需要改协议（注册、发令牌、客户端存储），属于较大改动，建议在服务器恢复、生产数据稳定后再做。
