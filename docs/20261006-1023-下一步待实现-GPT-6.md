## 1. 墓碑安全回收

当前 `_syncMeta.nodeTombstones` 与分组墓碑永久保留，`SYNC_TOMBSTONE_TTL_MS` 为无限。服务端只保存一份完整同步投影及版本，没有设备成员信息；客户端会把离线工作副本和远端合并。直接改成 60 天清理，会让长期离线副本复活已删除书签。

建议采用以下约束，而不是单独增加过期时间：

1. **设备登记**：服务端新增设备表，包含设备 ID、协议版本、状态、凭据摘要、确认版本、压缩代际和最近活动时间。首次接入必须下载基线并落盘，完成登记后才允许上传。
2. **持久确认**：客户端成功应用远端并持久保存本地副本后确认 revision（服务端版本）；仅仅 GET 成功不算确认。待发送队列必须完成重放或基于新基线重新构建，不能确认后继续发送较旧的整包。
3. **删除版本**：由服务端为每条墓碑记录首次提交的删除 revision。当前 `deletedAt` 是客户端逻辑时钟，不能直接替代服务端提交版本。编辑后再次删除时，必须更新对应删除版本。
4. **候选回收**：仅当所有有效设备确认删除版本，且没有未处理的旧协议设备，才能进入候选集。`lastSeen` 仅用于提示离线设备，不能自动把设备退役。
5. **压缩代际栅栏**：回收时同时递增 epoch（压缩代际），原子落盘压缩后的文档和设备状态。所有旧 epoch 的 PUT、旧 outbox 和迟到确认均被拒绝。设备必须下载压缩后的基线，再生成新一代变更；单凭最新 ETag 或“全部已确认”还不足以排除旧整包回推。
6. **显式退役**：用户决定退役设备，服务端撤销其独立凭据。旧设备重新接入先备份本地数据，再重新登记。推荐从云端重新初始化；若要保留离线编辑，进入独立冲突面板逐项选择，不能自动合并已失去删除证据的旧副本。
7. **身份边界**：当前共享 Token（访问令牌）保持不变。方案可先以“所有持有共享令牌的设备都可信”为前提做登记验证；启用退役后，写入接口还应要求独立设备凭据，避免已退役设备仅修改 ID 后继续写入。

### 迁移与回滚

- 启用前备份服务端状态、设备表、每台客户端的本地数据与 outbox。备份中的凭据和网址不得进入仓库。
- 第一阶段只收集设备/确认信息，不回收；旧客户端仍存在时继续永久保留。
- 第二阶段升级所有有效客户端，明确选择退役设备；启用 epoch 强校验，再做回收演练。
- 状态文档、设备表、删除索引和 epoch 应放在同一个原子状态文件中，避免多文件提交中断后不一致。
- 服务端回滚必须恢复整套状态；不能只恢复较老文档而保留较新的确认表。发生回滚后再次切换代际，迫使设备重新取基线。
- 墓碑字段精简可先独立评估，但删除类型、逻辑时钟、ID、位置与复活裁决信息不能随意移除；撤销所需原始内容应在本地备份中明确保留。

### 必测场景

| 场景 | 预期 |
|------|------|
| 一台设备离线超过 60 天 | 不因时间自动回收 |
| 下载成功但本地保存失败 | 不推进确认版本 |
| 所有设备确认后仍有旧 outbox | 旧 epoch 写入被拒绝 |
| 并发删除、编辑、再次删除 | 删除版本与字段时钟共同保证确定性 |
| 退役设备重新上线或更换 ID | 旧设备凭据失效，必须重新登记 |
| 旧协议客户端提交完整文档 | 阻止跨越压缩边界写入 |
| 回收落盘失败、服务端回滚 | 不发布部分提交，不接受过时确认 |
| 新设备携带旧导出文件 | 先建立新基线，再经显式导入决策处理 |

**待用户决定**：退役后重新接入，是“自动备份后从云端初始化”，还是“进入人工冲突处理”。选择前继续保留当前永久墓碑行为。
