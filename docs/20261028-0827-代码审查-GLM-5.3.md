## 发现一 [P1]：推送 412 重试不采纳新 etag，三次重试必然全部失败 — src/js/sync_engine.js:469-476

**场景**：设备 A 推送前先预拉取（`pushNowImpl` 开头两次 `readRemoteSyncDocument`，拿到 etag E1）。若设备 B 恰好在「预拉取之后、PUT 之前」这个窗口写入（服务端推进到 rev2/etag E2），A 的 PUT 因 `If-Match: E1` 失配返回 **412**，且 412 响应体/响应头都带有新 etag E2（`scripts/sync-server.mjs:670-685`）。

**缺陷**：`pushNowImpl` 的 412 分支只更新了 `baseRevision` 并合并远端文档，**从未把 `writeErr.etag` 写回 `_status.lastRemoteEtag`**（对比：`resolveDocConflict` 的 local 分支在 sync_engine.js:662 就正确采纳了）。于是重试第 2、3 次的 PUT 仍带 `If-Match: E1` → 仍然 412 → 三次重试（`SYNC_REVISION_RETRY = 3`）全部耗尽，`pushNow` 以 `precondition_failed` 失败、落入 outbox、状态栏显示同步错误。整段 412 重试循环**在任何输入下都不可能成功**，是死代码；恢复只能靠下一轮 `pushNow` 开头的新鲜预拉取。

**复现**（`/tmp/verify-412-retry.mjs`，本机实测输出）：

```
[seed] rev1 etag: "eda2f3da8edd22f33da34ee2737b52b7"
[proxy] injected device-B write rev2, etag: "dfe324e86248d583519ff2d5ebceeff3"
[proxy] PUT #1 If-Match: "eda2f3da8edd22f33da34ee2737b52b7"
[proxy] PUT #2 If-Match: "eda2f3da8edd22f33da34ee2737b52b7"   ← 仍用旧 etag
[proxy] PUT #3 If-Match: "eda2f3da8edd22f33da34ee2737b52b7"   ← 仍用旧 etag
[pushNow] {"ok":false,"reason":"precondition_failed"}
```

**修复建议**（一行）：412 分支内加 `if (writeErr.etag) _status.lastRemoteEtag = writeErr.etag;`。另建议补一条回归测试：代理在首个 PUT 前注入并发写，断言 `pushNow` 最终 `ok:true`（现有测试只覆盖了 `resolveDocConflict` 的 412，见 tests/sync-engine.test.js:200，`pushNow` 的 412 路径零覆盖）。

## 发现二 [P2]：412 重试推送的是合并前的过期本地快照 — src/js/sync_engine.js:443、447

**场景**：同上触发 412 后，`applyRemoteDoc(..., "push_412_pull")` 会把远端变更合并进本地并 `_setData(merged.state)`——而 `app.js:3184-3186` 的 `setData` 是**整体替换引用**。但重试循环里的投影源 `latest` 是循环外（第 443 行）捕获的旧引用，`toSyncDocument(latest, ...)` 仍投影**合并前**的本地数据。

**后果**：即使修好发现一（重试能成功），重试推上去的整包也**不包含刚合并进来的远端独有变更**（例如设备 B 新增的书签会被这次推送从服务端临时抹掉）。靠「变更来源设备下次再推」能最终收敛（merge 对本地独有节点取保留侧、墓碑按时钟裁决，已核对 `sync_merge.js:60-133`），但期间其它设备会看到「新增项消失又回来」的抖动，与 412 修复叠加时更明显。非 412 的普通重试路径（第 498-503 行 `push_retry_pull` 合并后）同样受影响。

**修复建议**：把 `const latest = _getData();` 移入循环内每次重取（循环末尾的 outbox 兜底在第 509 行已经是每次现取的写法，可对齐）。

## P3 备忘（低影响，顺手可修）

1. `sync_engine.js:246` 幂等键拼了 `Date.now()`，同一逻辑写入的每次重试都是新键，服务端幂等缓存（sync-server.mjs:648-650、725-732）永远命中不了——机制形同虚设，无害但易误导后人。
2. `sync_engine.js:303` `remote.reason === "incomplete_remote" ? "error" : "error"` 三元两臂相同，死代码。
3. `saveState()`（sync_engine.js:188-208）没持久化 `lastRemoteEpoch`：刷新页面后回到 0，直到下次拉取才恢复。当前所有推送路径都会先拉取（第 422 行），epoch 在写前必然新鲜，所以暂无实际后果；若以后出现「不预拉直接推」的路径会放大成必现 409。
4. `sync-server.mjs:76、400` 的 CORS `Allow-Headers/Expose-Headers` 未声明 `X-Sync-Epoch`：三端 manifest 均有 `<all_urls>` host_permissions，扩展 fetch 不走 CORS，无影响；但若将来有网页端客户端会踩坑。
