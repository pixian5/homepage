# 一个浏览器改的内容被另一个浏览器改回去（2026-11-03 15:55）

## 现象

在多浏览器（Chrome / Safari / 火狐）里改一条书签，过一会儿发现**被另一个浏览器的旧数据替换回去了**。

## 根因：推送前「要不要先合并」判断错了

服务端不做合并，它只接受整份文档的 PUT（配合 If-Match）。
所以「不覆盖别人」这件事**全靠客户端在推送前先合并**。

而原来的判断是**看版本号记账**：

```js
if (baseRevision > (_status.lastRemoteRevision || 0)) {
  await applyRemoteDoc(remote.doc, deviceId, "push_pre_pull");   // 先合并
}
```

问题出在：`lastRemoteRevision` 是**每个页面实例各自的内存状态**，而数据是整个浏览器共享的。

想象这条时间线：

1. 标签页 A 拉取到 revision 84，合并、落盘，把 `lastRemoteRevision = 84` 写进存储。
2. 标签页 B 是更早打开的，内存里的 `data` 还是 revision 80 的样子；
   但它每次推送前都会 `loadState()`，于是也读到了 `lastRemoteRevision = 84`。
3. B 因为某个本地动作（改图标、拖动、或者干脆是防抖推送）触发推送：
   `baseRevision(84) > lastRemoteRevision(84)` 不成立 → **跳过合并**。
4. B 把内存里那份**旧快照**整包 PUT 上去，服务端照单全收。
5. 于是 A 刚改的东西没了。

多浏览器的场景完全一样：每个浏览器是一个独立实例，但共享同一套「版本号已跟上」的错觉。

**版本号能证明「服务器到了哪一版」，却证明不了「我这个实例的内存数据已包含那一版」。**
这就是整件事的破绽。

## 修法：改看内容，不看记账

推送前直接比内容——本地投影与远端那份是否完全一致：

```js
const sameAsRemote = isContentEqualToRemote(_getData(), remote.doc, _status.docId);
if (!sameAsRemote) {
  // 只要不一致，就先把远端合并进来，再基于合并后的数据推送
  await applyRemoteDoc(remote.doc, deviceId, "push_pre_pull");
  // 重取一次拿到最新 revision / etag
}
```

`isContentEqualToRemote()` 复用 26.5.1 那套做法：用**远端的** `deviceId` / `revision` / `writtenAt`
重建本地文档再算 `contentHash`，内容一致才会相等。

这样无论版本号怎么记账，只要内存数据真的旧了，就一定会先合并。
合并采用字段级时钟（`titleUpdatedAt` / `urlUpdatedAt`），旧快照里的旧标题会被正确判负，
不会顶掉别人的新修改。

### 顺带的好处

- 26.5.1 的「内容一致就不写」仍然生效：合并后如果内容已经等于远端且队列为空，直接跳过写入。
- 不再依赖 `lastRemoteRevision` 的正确性，少了一类难查的时序 bug。

## 回归测试（含变异验证）

`tests/sync-engine.test.js` 新增 `sync_engine stale snapshot protection`：

1. 本机推一版建立基线；
2. 模拟另一台设备改标题并推送；
3. **把本机状态的 `lastRemoteRevision` 和 `lastRemoteEtag` 改成指向对方那一版**
   （模拟「记账跟上了、内存数据还是旧的」）；
4. 本机推送 → 断言远端标题仍是对方的「Written by peer」。

**变异验证**：把修复临时改回 `baseRevision <= lastRemoteRevision` 的旧判断，该用例立刻失败
（`AssertionError: 旧快照不能覆盖别处的新修改`），改回修复版即通过。说明这条测试确实咬住了这个 bug。

全量：**258 项全过**；`npm run check` 85 个文件无告警。

## 另一个隐患（已记录，本次未改）

线上 45 个节点里有 **4 个缺 `titleUpdatedAt`**、**2 个缺 `urlUpdatedAt`**（早期版本留下的老数据）。

合并时字段时钟缺失会退回用 `updatedAt`，而 `updatedAt` 会被「改图标」之类的动作推进——
这会让一个**没被改过的旧标题**带上一个很新的时钟，理论上仍可能压过别处真正的标题修改。

彻底解决需要两条一起做：
1. 合并时对缺失字段时钟的节点做显式处理（不能用实体时钟冒充字段时钟）；
2. 让「只改图标」不要推进实体时钟，或拆出独立的 `iconUpdatedAt`。

这两条都会动合并语义，需要单独设计 + 补测试，没有塞进这次修复。
