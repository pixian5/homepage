### 1.1 本轮发现并修复：dist 构建入口自 26.1.8 起损坏

- 现象：`./dist/run-build.command` 立即失败，报 `dist/lib/safari-signing.sh: No such file or directory`，退出码 1（第一次构建即踩中）。
- 根因：26.1.8 把 `build-macos.command` 手动同步到 `dist/` 时，**漏掉了它第 33 行 source 的 `lib/safari-signing.sh`**（`scripts/lib/` 有，`dist/lib/` 没有）。
- 修复：① 补齐 `dist/lib/`；② 在 `scripts/build-macos.command` 末尾新增自动同步步骤（构建入口 + `lib/` 一起同步到 dist），杜绝再犯。修复后已用 dist 入口完整重建验证。

## 三、核心新发现：生产同步不可达的根因定位

### 3.1 证据链（2026-10-28 实测）

| # | 探测 | 结果 |
|---|---|---|
| 1 | 本机 `curl https://sf.sbbz.tech:58443/health` | TLS `unexpected eof`（与 10-26 相同） |
| 2 | 本机 `dig sf.sbbz.tech` | **198.18.30.67** —— fake-IP 网段（198.18.0.0/15），域名被本机代理软件接管 |
| 3 | DoH（dns.google）查真实 IP | `sf.sbbz.tech → 146.190.141.137`（DigitalOcean） |
| 4 | 本机 `--noproxy --resolve` 直连真实 IP | TCP「通」但 TLS 仍 eof；SSH 到 `aws.sbbz.tech` 真实 IP（3.144.244.220）同样握手即断 —— TUN 代理会本地假握手，**本机结论不可信** |
| 5 | check-host 第三方节点 TCP 58443 | 西班牙/荷兰/俄罗斯 → **全部 Connection timed out** |
| 6 | check-host 第三方节点 ping | 法国/伊朗 → **全部 OK**（机器活着） |
| 7 | check-host 第三方节点 TCP 22 | 西班牙/新加坡 → **全部 Connection timed out** |

### 3.2 结论

**服务器 146.190.141.137 在线（ICMP 正常），但 22 与 58443 端口从全球多个节点全部超时** —— 入站 TCP 被整类丢弃。最可能是：

1. DigitalOcean Cloud Firewall 规则变更/丢失，或 ufw 把入站全拦；
2. 或 sshd 与同步服务同时停止（概率低，两者同时挂更像是防火墙）。

这是**服务器级故障**，与扩展代码无关。另有一个重要教训：**本机代理的 fake-IP + TUN 假握手会制造「端口能连」的假象**，判断服务器死活必须用第三方节点交叉验证（本轮就靠这一步纠正了误判）。

### 3.3 恢复 runbook（需要 DigitalOcean 控制台权限）

```text
1. DO 面板 → 检查该 Droplet 的 Cloud Firewall 是否绑定、规则是否放行 22/TCP 与 58443/TCP
2. 若面板看不出 → 用 DO 恢复控制台/VNC 进入系统：
   ufw status verbose
   systemctl status homepage-sync
   ss -tlnp | grep -E '58443|8787'
3. 恢复网络可达后，先备份：tar czf homepage-sync-backup.tgz /var/lib/homepage-sync 并拉回本机
4. 部署仓库最新 scripts/sync-server.mjs（生产服务端仍是 8-27 之前的旧版：
   没有设备表 / deletions / reclaim / epoch，必须升级才能承接 26.1.5+ 客户端协议）
   参考 scripts/setup-sync-server.sh（服务名 homepage-sync，数据目录 /var/lib/homepage-sync）
5. systemctl restart homepage-sync，从外部 curl /health 验证
6. 每台客户端手动「立即同步」一次：pushNow 不受 outbox attempts=12 上限限制，
   成功即清空 outbox（sync_engine.js:521 / 462）
7. 验证设备登记：GET /v1/sync/devices 应出现各设备
```

## 四、下一步开发建议（按优先级与依赖排序）

### 第 0 步：恢复生产同步服务（约 0.5 天，最高优先级）

只有用户能进 DO 控制台。上节 runbook 可直接执行。**这条不解决，设备表、墓碑回收、同步可见性全都只在本地测试里成立。**

### 第 1 步：P1-1 服务端备份/恢复脚本（0.5 天）——升级生产前的硬前置

- `scripts/backup-sync-state.sh`：在服务器上 tar 状态目录、保留最近 N 份，并支持 scp 拉回本机；
- `scripts/restore-sync-state.sh`：停服务 → 校验 JSON → 替换 → 启动 → `/health` 验证；
- 把「部署前先备份」写进 setup 脚本注释与 server-sync.md。

### 第 2 步：P0-3 + P0-2 客户端可见性（约 1 天）

- **失败提示条**：同步状态为 `error` 超过阈值（如 24 小时）或 outbox `attempts` 达上限时，新标签页顶部显示可关闭横幅，带「立即重试」（调 `pushNow()`）与「查看设置」。本轮两个月断同步用户毫无感知，就是缺这个；
- **跨标签页状态**：`app.js:423` 的 storage 监听增加 `SYNC_STATE_KEY`，变化时刷新状态栏与冲突按钮。

### 第 3 步：P1-3 CI 加 Firefox 冒烟（0.5 天）

- CI 增加 Firefox 安装（`browser-actions/setup-firefox` 或 apt 版），跑 `npm run test:browser-smoke -- firefox`；
- Safari 继续留本机专项验证。

### 第 4 步：P3 缓存瘦身（1 天）

- 删除书签时同步移除图标缓存条目；启动时按当前书签 URL 集合清孤儿；
- 背景缓存只保留当天与前一天。

### 第 5 步：P2-2 拆拖拽控制器（2～3 天，可分次）

- 先为拖拽/放置计算补一组纯函数测试，再搬代码；
- 每拆一块同步更新 `scripts/firefox-modules.json` 并跑 Firefox 冒烟。

### 第 6 步：P5 设备退役 + 独立凭据 + 首次生产回收演练（2～3 天 + 全设备协调）

- 服务端退役端点（拒绝退役设备写入）、设备级凭据替换共享 Token；
- 首次生产回收流程：全设备在线 → `GET /v1/sync/devices` 确认进度 → `reclaim dryRun` 核对候选 → 备份 → `dryRun:false` → 各端确认新 epoch。

### 顺手项（建议但不阻塞）

- 生产 `/health` 接入极简监控：服务器 cron 定时对比 `revision/updatedAt`，停滞超 48 小时推 bark 通知（用户已有 bark 通道），避免再次「断两个月才发现」。
