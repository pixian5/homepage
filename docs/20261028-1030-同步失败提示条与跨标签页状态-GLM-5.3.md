## 二、判定规则（设计与取舍）

| 情形 | 是否提示 | 理由 |
|---|---|---|
| 同步正常 | 不显示 | — |
| `error` 但持续 < 10 分钟 | 不显示 | 网络抖动很常见，一律弹窗会变成噪音 |
| `error` 持续 ≥ 10 分钟 | **显示** | 真正的故障 |
| `error` 且无时间戳（老状态） | **显示** | 宁可多提醒，不能静默 |
| outbox `attempts` 达上限（自动重试已放弃） | **显示** | 硬故障，用户不手动点就永远不会恢复 |
| 用户关闭后 24 小时内（软故障） | 不显示 | 尊重用户 |
| 用户关闭后 2 小时内（硬故障） | 不显示 | 折中：既不每刷新都弹，也不长期静默 |

**关键取舍**：硬故障最初设计成「关闭后仍每次都弹」，实测后改成 2 小时静默——完全不理会关闭会让用户只能无视提示条，静默太久又会重演「断链两个月」。2 小时是折中点。

## 三、交互

- **立即重试**：拉一次远端拿新基线 → 手动推送。`pushNow` 不受 outbox attempts 上限限制，这是**用户唯一的自救入口**；重试期间提示条保持可见并显示「正在重试…」；
- **查看设置**：直接打开设置面板；
- **关闭**：记录 `dismissedAt`。

## 四、跨标签页状态同步

`attachStorageListener` 原来只监听 `homepage_data`，现在同时监听 `homepage_sync_state` 与 `homepage_sync_outbox`，任一变化就刷新提示条。这样另一个标签页解决冲突或后台推送完成后，本页状态立刻跟上。

注意：同步状态键的监听不受 `persistInFlight` / `suppressStorageUntil` 保护（那两个只针对数据写入），否则后台写入期间的同步事件会被误吞。

### 发现的缺陷（已修）

**「查看设置」按钮点击必然抛 ReferenceError**（`src/js/app.js` 提示条创建处）：

```js
onOpenSettings: () => openSettingsModal(),   // ❌ app.js 里没有这个函数
```

`openSettingsModal` 定义在 `settings-controller.js:222`，是控制器内部函数；`app.js` 侧只能通过 `settingsCtl.openSettingsModal()` 访问（第 3455 行已有正确写法）。原文会抛 `ReferenceError: openSettingsModal is not defined`，按钮点了毫无反应——而「查看设置」正是提示条给用户的另一个出口，等于半个功能失效。

已改为 `onOpenSettings: () => settingsCtl?.openSettingsModal()`，并确认初始化顺序正确（`settingsCtl` 在 3069 行创建，提示条在 3279 行创建）。
