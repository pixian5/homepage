# Safari 里出现两个「我的首页」扩展：排查与修复

> 记录时间：2026-10-08 21:20　模型：GPT-6
> 触发现象：用户在 Safari 设置里启用扩展后，看到**两个**「我的首页」扩展条目。

## 一句话结论

不是陈旧注册残留，而是 **Safari 实际加载的是构建产物目录里那份 `.app`，不是 `/Applications` 的正式版**。
两个条目由此而来。修法是让构建产物里那份不再存在，并把该动作固化进构建脚本。

## 排查过程（按证据顺序）

### 1. 先否定「陈旧注册残留」这个假设

项目里原本就有 `clean-safari-homepage-registrations.py`，专门清理两个已知陈旧 key：

```
com.aeroluna.homepage.safari.extension (PSTNW3UN4R)   ← 旧团队
com.aeroluna.homepage.safari.extension (UNSIGNED)     ← 未签名残留
```

用 Python 精确解析（不用 `grep`，避免误判）三个 plist：

| 文件 | 条目总数 | 含 aeroluna 的 key |
|------|---------|-------------------|
| `WebExtensions/Extensions.plist` | 16 | **仅 1 个**：`... (WY97WQFBKC)` |
| `AppExtensions/Extensions.plist` | 2 | 0 |
| `Profiles/DefaultProfile/WebExtensions/Extensions.plist` | 5 | 0 |

再逐值递归搜索 `PSTNW3UN4R` / `UNSIGNED` 两个字符串：**命中数 0**。

> **更正一处误判**：早先用 `plutil -p | grep` 时确实看到了 `(PSTNW3UN4R)` 和 `(UNSIGNED)`，
> 但那属于**别的扩展**的团队标识，不是本项目的残留。
> 教训：查 plist 要用 `plistlib` 解析后按 key 判断，别用 grep 扫文本。

注册层是干净的，`Enabled = True`，不需要清理。

### 2. 真正的根因：进程路径不对

`pluginkit` 显示注册路径正确：

```
com.aeroluna.homepage.safari.extension(25.9.3)  →  /Applications/我的首页 Safari.app/.../我的首页 Safari Extension.appex
```

但实际跑起来的进程是：

```
/Users/x/code/homepage/dist/safari-app/build/Build/Products/Release/
  我的首页 Safari.app/Contents/PlugIns/我的首页 Safari Extension.appex   ← 构建产物！
```

**Safari 加载的是构建目录那份。** 危害不只是列表多一项：

- 续签后 `/Applications` 那份更新了，Safari 却仍在跑构建目录里的旧副本 → 7 天到期后依旧失效；
- 用户以为自己在用正式版，实际用的不是。

### 3. 为什么原来的 `lsregister -u` 不够

两个脚本原本都会在安装后注销源路径：

```bash
lsregister -u "${APP_PATH}"
```

实测证明这挡不住——Safari 仍从构建目录加载。可靠做法是**物理删除**构建产物里那份。

## 修复

### 立即处理

1. 优雅退出 Safari（`osascript -e 'tell application "Safari" to quit'`）。
2. 删除构建目录里的两份产物：
   ```
   dist/safari-app/build/Build/Products/Release/我的首页 Safari.app
   dist/safari-app/build/Build/Products/Release/我的首页 Safari Extension.appex
   ```
3. 重开 Safari。

### 固化进脚本

在 `scripts/lib/safari-signing.sh` 新增公共函数，完整构建与快速续签共用：

```bash
prune_safari_build_products() {
  local configuration="${1:-Release}"
  local products_dir="${SAFARI_BUILD_DIR}/Build/Products/${configuration}"
  local app="${products_dir}/${SAFARI_APP_NAME}.app"
  local appex="${products_dir}/${SAFARI_APP_NAME} Extension.appex"
  local removed=0 target
  for target in "${app}" "${appex}"; do
    if [[ -e "${target}" ]]; then rm -rf "${target}"; removed=$((removed + 1)); fi
  done
  echo "[sign] Pruned ${removed} build product(s); Safari will only see the /Applications copy"
}
```

调用点：

- `scripts/build-macos.command`：拷贝进 `/Applications` 之后（`lsregister -u` 之后）
- `scripts/safari-refresh-signing.sh`：同上

单元测试已验证：构造 3 个产物（含 1 个无关文件）→ 删掉 2 个目标、保留无关文件；
重复调用第二次返回 `Pruned 0`，幂等。删掉后 xcodebuild 下次会重新生成，不影响增量构建。

## 遗留观察点：共享数据文件未更新

`~/Library/Group Containers/group.com.aeroluna.homepage.safari/homepage-data.json`
停留在 **2026-08-14 16:15**，新标签页加载后也没有变化。

**暂不能据此判定 App Group 不通**，因为：

- 扩展只在数据变更时才写，加载页面本身不一定触发写入；
- 新标签页已成功渲染扩展页面，说明扩展进程与资源加载正常。

**判据**：看新标签页里有没有你**原有的书签和设置**。
有 → 读通了，只是没写操作；空白/默认值 → App Group 确实没通，需进一步处理。

**结论（已验证）**：用户确认新标签页**有**历史书签与设置 → App Group 读通，
扩展 profile 缺 `application-groups` 属无害。详见
[App Group 数据共享验证](20261008-2130-AppGroup数据共享验证-GPT-6.md)。

相关的可疑点：扩展内嵌 profile 的 Entitlements 里**没有** `com.apple.security.application-groups`
（宿主 App 那份有），而扩展的签名 entitlements 里是有的。详见
[关 SIP 与 Gatekeeper 能否免签名](20261008-2115-关SIP与Gatekeeper能否免签名-GPT-6.md) 的「发现隐患」一节。
