**是，本轮全部使用本机临时启动的同步服务，不连接任何远程或生产服务器，也不需要联网。**
上一轮盘点里“未覆盖”的三项——冲突弹窗三选一、同步包导入导出、周期同步——现已全部补测通过。

## 本地服务器怎么起的

三个端到端脚本都在测试内部自己拉起服务端，参数固定为：

```js
HOST: "127.0.0.1"          // 只监听回环地址，局域网也访问不到
PORT: <系统分配的空闲端口》  // 每次换端口，避免撞上正在运行的服务
TOKEN: <本次测试专用>       // 与脚本内置值一致，跑完即丢弃
DATA_FILE: <临时目录>/state.json  // 独立状态文件，绝不碰 data/homepage-sync-state.json
```

退出时脚本会结束子进程，并删除整个临时目录。**没有使用、也没有改动你真实的同步数据和服务器。**

| `test:firefox-sync-ui` | 本机临时服务 | 临时 | 通过 |
| `test:firefox-sync-flows`（新增） | 本机临时服务 | 临时 | 三个分支全部通过 |

## 新增：`test:firefox-sync-flows`

```bash
npm run test:firefox-sync-flows                 # 默认 merge
node scripts/run-firefox-sync-flows.mjs --choice=local
node scripts/run-firefox-sync-flows.mjs --choice=remote
```

每个分支都会：预置一个 **docId 与浏览器本地不同** 的云端文档 → 触发真实 `doc_conflict` →
点开冲突弹窗点对应按钮 → 再用同步包导出/导入 → 最后验证周期同步。

### 三个分支的实测结果

| 分支 | 弹窗按钮 | 断言 | 结果 |
|---|---|---|---|
| merge | 合并 | 云端书签与本地书签**都保留** | ✅ |
| local | 本地覆盖云端 | 本地书签保留 | ✅ |
| remote | 使用云端 | 云端书签已应用到本地 | ✅ |

三个分支都额外验证了：

- 冲突状态出现时「解决冲突」按钮可见（`btnSyncResolveConflict` 不再 hidden）；
- 同步包导出成功（merge 3115 字节 / local 2531 / remote 2228，尺寸随数据不同而不同）；
- 手动删除书签后，用同步包导入能恢复**该分支保留下来的那本书签**；
- 周期同步切到 1 分钟后，`lastPullAt` 自动前进（定时器真的在跑）。

### 周期同步为什么要覆写可见性

`startSyncInterval` 有一条明确设计：`document.visibilityState === "hidden"` 时不拉取，
避免后台标签页偷偷消耗流量。无头 Firefox 的可见性恒为 `hidden`，
所以测试里把 `visibilityState` 显式覆写为 `visible`，只验证“到点会拉取”这条逻辑。
真实窗口的可见性行为（切到后台就暂停）不在自动化范围内，需要人工确认。

## 同步包的两种入口

本轮验证的是 **剪切板入口**（`btnSyncExportBundle` / `btnSyncImportBundle`）。
文件入口（`btnSyncExportFile` / `btnSyncImportFile`）走的是同一个 `exportSyncBundle` /
`importSyncBundle`，只有“下载文件 / 读取文件”的外壳不同；无头模式下文件选择器不可脚本化，
本轮**没有**端到端覆盖，只由单元测试覆盖了核心合并逻辑。

## 鉴权与异常分支

本轮所有调用都带正确 Token。以下仍未在浏览器内实跑：

- 错误 Token（401）
- 服务端 500 / 磁盘写满
- 请求超时（10 秒）
- outbox 重试耗尽

这些只有 `tests/sync-http.test.js` 与 `tests/sync-engine.test.js` 的单元测试覆盖，
缺“真实浏览器里点按钮会看到什么提示”的验证。
