# 配置文件（provisioning profile）为何必需：实测矩阵与三条出路（2026-10-08 21:35）

> **结论已被修正**：本文档的六组实验用的是**裸 Mach-O 命令行探针**，
> 对 `.app` / `.appex` 这类 bundle 不成立。实测证明 bundle 无需 profile，
> 沙箱与 App Group 照常生效，7 天续期可以彻底去掉。
> 详见 [去掉内嵌描述文件](20261008-2150-去掉描述文件免7天续期-GPT-6.md)。
> 下文保留原样，用于记录"探针形态决定结论"这个教训。

## 问题的准确表述

用户问：能不能**不要配置文件**？如果不要，是不是就不用每 7 天重签了？
（背景：本机 SIP 与 Gatekeeper 均已关闭。）

答案是分两层的：

1. **配置文件不能去掉**，去掉之后扩展进程会被 AMFI 直接杀掉（实测 exit=133）。
2. **7 天这个周期是可以去掉的**，但换的不是"去掉配置文件"，而是换一条**不需要配置文件的签名体系**
   （Developer ID + 公证），代价是付费账号。

关键区分：**签名证书 ≠ 配置文件**。

| | 是什么 | 本机有效期 |
|---|--------|-----------|
| 签名证书 `Apple Development: ibjxk0@gmail.com (YGR8677YMA)` | 证明"谁签的"，放在钥匙串 | **到 2027-08-04**（1 年） |
| 配置文件 `Mac Team Provisioning Profile: com.aeroluna.homepage.safari` | 内嵌进 `.app`，证明"Apple 授权了这些权限" | **7 天** |

7 天瓶颈来自后者，而且它只对**免费 Apple ID** 成立。

## 实测矩阵（SIP 已关 + Gatekeeper 已关 的当前机器上跑的）

探针：Swift 命令行程序，读 App Group 容器里的 `homepage-data.json`，成功则打印
`READ-OK bytes=36685` + `PROCESS-ALIVE`。
`exit=133` = 128+5 = SIGKILL，即被 AMFI 杀掉。

| 组 | 签名身份 | entitlements | 内嵌 profile | 结果 |
|----|---------|--------------|--------------|------|
| A | Apple Development | 沙箱 + App Group | **无** | **exit=133 被杀** |
| B | adhoc（`-`） | 沙箱 + App Group | 无 | **exit=133 被杀** |
| C | Apple Development | **空**（无受限权限） | 无 | exit=0 存活 |
| D | Apple Development | 沙箱 + App Group | **有**（真 .app bundle） | exit=0 存活，读到 36685 字节 |
| E | Apple Development | **仅 App Sandbox** | 无 | **exit=133 被杀** |
| F | Apple Development | 仅 App Group（无沙箱） | 无 | exit=0 存活 |

复核当时机器状态：`csrutil status` = **disabled**，`spctl --status` = **assessments disabled**。

## 从矩阵里读出来的机制

1. **杀进程的不是"没签名"，而是"没被授权的受限权限"**。
   A 组有真证书、真签名，照样 133；C 组同样的签名，只是 entitlements 为空，就活得好好的。

2. **触发点是 `com.apple.security.app-sandbox`，不是 App Group**。
   E（只沙箱）死，F（只 App Group）活。
   也就是说：AMFI 对"受限 entitlement"做**授权校验**，要求 Apple 签发的 provisioning profile
   为它背书；App Sandbox 属于受限项，所以无 profile 声明沙箱 = 直接 SIGKILL。

3. **Safari 扩展躲不开这一条**。`.appex` 强制 App Sandbox，实测两端 entitlements 都是
   `com.apple.security.app-sandbox = true`：

   ```
   宿主 com.aeroluna.homepage.safari            → app-sandbox=true
   扩展 com.aeroluna.homepage.safari.extension  → app-sandbox=true
   ```

   所以**宿主和扩展都必须带 profile**，一个都不能省。

4. **关 SIP 和关 Gatekeeper 完全不影响这个校验**（A/B/E 三组就是在两者都关的情况下被杀的）。
   Gatekeeper 只在**首次打开**时评估（`spctl`）；SIP 保护的是系统路径；
   真正每时每刻校验 entitlement 授权的是 **AMFI**，关 SIP 不停 AMFI。
   与 [关 SIP 与 Gatekeeper 能否免签名](20261008-2115-关SIP与Gatekeeper能否免签名-GPT-6.md) 的结论一致。

## 三条出路对比

| 方案 | 还要 profile 吗 | 维护频率 | 成本 | 备注 |
|------|-----------------|---------|------|------|
| **① 现状：免费账号 + 自动续期** | 要 | 每 7 天（launchd 已自动跑） | 0 | Safari 必须在续签那一刻退出，见「残留隐患」 |
| **② 付费账号 + Apple Development profile** | 要，但有效期变成 1 年 | 每年一次 | ¥688/年 | 付费后 profile 的 TTL 不再是 7 天；具体天数以实签后 `safari-signing-status.py` 为准 |
| **③ 付费账号 + Developer ID 签名 + 公证** | **不需要** | 到证书过期为止（数年） | ¥688/年 | Mac 第三方 app 的标准分发方式，`embedded.provisionprofile` 根本不存在；需联网公证一次并 staple |

**方案③ 是唯一真正"没有配置文件"的路**。它绕开 AMFI 的 profile 授权校验的原理是：
Developer ID 签名属于分发签名，entitlements 直接由签名承载，不再需要 profile 背书
（所有 Mac 第三方 app 都没有 `embedded.provisionprofile`，就是这个原因）。

不推荐的第四条路：`nvram boot-args="amfi_get_out_of_my_way=1"`（需 SIP 关闭 + 重启）。
它能让无 profile 甚至 adhoc 的签名跑起来，但等于**全局关掉 AMFI 校验**，安全性归零，
且一旦恢复 SIP 就失效。不建议为省 7 天续期做这个交换。

## 残留隐患（方案① 的真实风险）

`scripts/safari-refresh-signing.sh` 在 **Safari 运行时直接跳过**续签（第 91、169 行，
目的是避免把内存里的旧扩展状态写回、制造幽灵条目）。

后果：如果你 **Safari 连着好几天不退出**，两次定时任务（09:00 / 21:00）都会跳过，
profile 到期那天扩展就会静默失效——正是换机那次遇到的现象。

可改进方向（尚未实施）：距到期 ≤2 天时不再跳过，改成"重签 + 明确提示重启 Safari"，
因为重签 /Applications 里的 .app 本身不需要 Safari 退出，只有**加载新签名**需要重启 Safari。
