## 二、排查过程：`invalid_doc_id`

切换后首次同步稳定报错：

```json
{"status":"error","lastError":"{\"error\":\"invalid_doc_id\"}","docId":null}
```

服务端日志确认收到的 `docId` 是**空字符串**：

```
[DEBUG] validate failed: invalid_doc_id | docId= "" | typeof= string | schema= "homepage.sync.doc.v1"
```

### 排查路径（多数是弯路，记录下来避免重犯）

| 假设 | 验证 | 结论 |
|---|---|---|
| 服务端校验有问题 | 手工构造合法文档 PUT | ❌ 返回 200，服务端正常 |
| 投影函数丢 docId | Node 里调 `toSyncDocument` | ❌ 输出 docId 正确 |
| Safari 的 `toSyncDocument` 异常 | 在扩展内动态 import 调用 | ❌ 输出 docId 正确 |
| deviceId 逻辑问题 | 读代码 + Node 模拟 | ❌ 正常 |
| **旧状态残留** | 清 `homepage_sync_state` 后重试 | ⚠️ 部分有效 |

真正的触发条件：**`homepage_sync_state` 里存着 `docId: null`**。引擎每次同步前 `loadState()` 会把 storage 的值展开覆盖内存 `_status`，于是 `docId` 被重置为 null。虽然 `pushNowImpl` 里有 `if (!_status.docId) createDocId()` 兜底，但 `pullNow` 的 `no_remote` 分支在调用 `pushNowImpl` **之前**已经 `saveState()` 把 null 落盘了，中间存在窗口。

清掉 `homepage_sync_state` 与 `homepage_sync_outbox` 后，同步一次成功：

```json
{"ok":true,"revision":1,"reason":"probe_manual"}
```

### 附带发现：多标签页会加重问题

排查时 Safari 开着 **3 个扩展标签页**，多个引擎实例竞争同一份 `homepage_sync_state`：一个清空后另一个用旧值推送，错误反复出现。**排查同步问题时先确保只有一个扩展标签页。**

## 四、遗留问题（建议下轮修）

`pullNow` 的 `no_remote` 分支存在一个真实的时序缺陷：它先 `saveState()` 落盘 `docId: null`，再进入 `pushNowImpl` 生成 docId。若在两者之间发生页面重载或多标签页竞争，就会把 null 当作有效 docId 推送，被服务端以 `invalid_doc_id` 拒绝。

**建议修复**：在 `pullNow` 开头（`loadState()` 之后、任何 `saveState()` 之前）就确保 `docId` 存在：

```js
await loadState();
if (!_status.docId) _status.docId = createDocId();
```

这样任何路径都不会再出现空 docId。同时建议在 `toSyncDocument` 侧对空 docId 做防御（返回错误而非空串），并在服务端日志里带上接收到的字段便于排查。

本轮未改代码（用户只要求切到本地服务器），已记录为下轮首个修复项。
