### 1.2 关键设计

- **文档与设备表同一次落盘**：避免只写一半导致状态不一致。
- **确认不能超前**：`confirmedRevision > state.revision` 返回 409，防止伪造未来确认。
- **推送即确认**：PUT 成功说明该设备已持有新版本，直接记录，减少一次往返。
- **旧状态文件兼容**：缺 `devices`/`epoch` 时按空表/0 补齐，**只读迁移，不改盘**。
- **不回收任何数据**：本阶段只采集，墓碑仍永久保留。

### 1.3 客户端接入

- `sync_http_transport.js` 新增 `httpConfirmSyncState()`。
- `sync_engine.js`：拉取成功且本地保存成功后、推送成功后，各确认一次；失败静默。
- 确认时机严格遵循方案要求：**只在本地持久保存成功后**，不会因为 GET 成功就确认。

## 二、设置面板拆分

### 2.1 结果

| 文件 | 拆分前 | 拆分后 |
|---|---|---|
| `src/js/app.js` | 4,813 行 | **3,763 行** |
| `src/js/settings-controller.js` | — | **1,387 行**（新增） |

搬出的内容：设置主面板、同步设置、导入/导出、备份管理、冲突弹窗。

### 2.2 拆分方式

**不用全局单例**，而是显式注入：

```js
settingsCtl = createSettingsController({
  getData: () => data,          // getter，控制器始终看到最新数据
  setData: (next) => { data = next; },
  getActiveGroupId / setActiveGroupId,
  state: { get settingsOpen() {...}, set settingsOpen(v) {...}, ... },
  consumeSkipAutoBackup,
  ui: { $, qsa, html, openModal, closeModal, ... },
  deps: { 同步、存储、数据工具等 },
});
```

- 数据只有一份（app.js 的 `data`），控制器通过 `getData()/setData()` 读写。
- 设置弹窗的开/关/保存状态用访问器回写到 app.js 的变量，避免两份状态。
- 模块用 IIFE 包裹：Firefox 版把所有模块拼成一个经典脚本，顶层 `const` 会重名。

### 2.3 过程中修掉的 3 个真实问题

1. **Firefox 打包器误删代码**
   `stripImports` 用 `^\s*import[\s\S]*?;` 匹配，把对象字面量里以 `import` 开头的属性
   （`importSyncBundle,`）连同后续整段代码一起吃掉。已改为要求 `import` 后必须跟空白。
   这个 bug 之前一直存在，只是没被这种写法触发。

2. **IIFE 作用域隔离**
   Firefox 经典脚本拼接下，新模块顶层的 `html`/`t`/`render` 与 `ui-utils.js` 重名，
   报 `Identifier 'html' has already been declared`。用 IIFE 只暴露一个全局名。

3. **依赖漏注入导致运行时崩溃**
   搬移时 `SYNC_INTERVAL_OPTIONS`、`DEFAULT_TOAST_DURATION_SECONDS`、`SETTINGS_SAVE_DELAY_MS`
   未注入，Safari 打开设置直接抛 `初始化失败`。已补齐并逐个在真实 Safari 中验证。

另外机械替换 `data.` 时误伤了字符串字面量（`[data-group]` → `[getData()-group]`），
已修复并做了新旧文件的字符串/属性全量比对，确认无遗漏。

## 四、下一步（墓碑回收第二阶段）

设备表已经能回答「谁确认到哪个版本」。第二阶段需要：

1. 服务端为每条墓碑记录**首次提交的删除 revision**（当前用的是客户端逻辑时钟）。
2. 计算候选回收集：所有有效设备确认版本 ≥ 删除 revision，且无旧协议设备。
3. 回收时递增 `epoch`，原子落盘文档 + 设备表。
4. 拒绝旧 epoch 的 PUT / outbox / 迟到确认。
5. 显式退役设备 + 独立凭据（可选，最后做）。

按方案文档要求，**第二阶段必须先备份服务端状态与每台客户端数据**。
