# 同步可靠性经验

## 核心模型

- 浏览器本地 `storage.local` 是离线工作副本；HTTP 服务端保存同步投影。
- PUT 使用 ETag / `If-Match` 做乐观并发控制；收到 412 后必须重新拉取、合并并使用新 ETag 重试。
- 每次重试都重新读取当前本地数据。合并可能整体替换数据引用，不能复用循环外的旧快照。
- merge、本地落盘或重试拉取失败时必须向上层返回错误，不能继续假装成功或覆盖远端。
- 网络失败、401、500、stale epoch 和 merge 失败要保持稳定错误分类；失败时 outbox 不得误清。

## 删除与回收

- 客户端删除先写墓碑，避免长期离线设备重新上传旧对象。
- 墓碑不按时间自动清理。服务端通过设备确认、退役状态和 epoch 计算候选。
- 真实回收必须人工核对、完成备份，并提供 `confirm: "RECLAIM"` 与 `maxCandidates`。
- 回收会递增 epoch；旧设备收到 stale epoch 后必须先拉取新基线，不能直接覆盖服务器。

## 排查顺序

1. 检查客户端 `lastError`、outbox 和最近同步时间。
2. 检查 `/health` 的 revision、epoch 和设备数量。
3. 检查 `/v1/sync/devices` 的确认进度与退役状态。
4. 区分 412 并发冲突、网络不可达、鉴权失败、服务端错误和 stale epoch。
5. 不直接删除本地或服务端状态；先备份，再做恢复或冲突处理。

## 必须验证

- 首次 412 后采用新 ETag 并推送合并快照。
- 连续冲突耗尽后返回明确失败并保留 outbox。
- 本地落盘失败后状态为 error，远端不会被错误覆盖。
- 同内容且无待推送项时不产生无意义 revision。
