# 「瞬间多次切换配置」的真凶：三处各自独立的坑叠加（2026-11-03 17:20）

## 用户的问题

> 瞬间多次立即切换配置，是不是因为我打开了多个浏览器的标签页，每次同步后以为对方最新？

**多标签确实是放大器，但它只是让问题更容易发生——真正的根因有三个，彼此独立。**

## 现场证据

| | 服务端 | Safari 本地 |
|---|---|---|
| `backgroundType` | **bing** | **color** |
| `_syncMeta.revision` | 97 | 97 |
| `backgroundType` 时钟 | 17:03:02.703 by Chrome | 17:03:02.703 by Chrome |

**版本号相同、时钟完全相同，值却不一样。** 这就是僵局的化石证据：
两端都认为「我已经是最新的那一版」，谁也不服谁。

## 三个坑

### 坑一：拉取短路靠版本号记账

26.5.2 加的「版本号没变就不合并」用的是**共享状态里的** `lastRemoteRevision`。
同一浏览器的多个标签页共享这份状态：A 标签拉到 88 之后，B 标签读到 88 就以为自己也最新了，
而 B 内存里的 `data` 可能还停在 84 —— 于是它永远不合并，界面一直显示旧设置。

### 坑二：时钟完全相同时「无条件采纳远端」

`mergeSettingsByClock` 原本是：

```js
if (!localHasClock || compareClock(rClock[key], lClock[key]) >= 0) {
  settings[key] = remoteValue;      // 相等也采纳远端
}
```

当两端时钟**完全一致**（`updatedAt` 与 `updatedBy` 都相同）但值不同时：

- A 拉 B → 采纳 B 的值；
- B 拉 A → 采纳 A 的值。

**两端各自把对方的值抄过来，然后对方又抄回去——永久来回切换。**
背景一会儿渐变一会儿 Bing、设置一跳一跳，就是这么产生的。

### 坑三：合并后「本地赢」却不推送

`applyRemoteDoc` 只在 `applied=true`（本地内容被改动）时通知上层；
如果合并结果是**本地赢**（本地时钟更新，保留本地值），本地内容没变 → `applied=false` → 不推。
于是服务端永远留着旧值，两端长期不一致，下一次拉取又重复同样的判断。

## 三处修法

### 1. 拉取也改成比内容

```js
if (isContentEqualToRemote(_getData(), remote.doc, _status.docId)) {
  ... unchanged ...
}
```

复用推送侧那套：用远端的 `deviceId` / `revision` / `writtenAt` 重建本地文档再算哈希。
内容一致才算「无变化」，不再被版本号记账带偏。

### 2. 时钟相同 → 按值本身定序

```js
const cmp = compareClock(rClock[key], lClock[key]);
if (cmp > 0) { ...采纳远端... continue; }
if (cmp < 0) continue;
// 时钟完全相同但值不同：取序列化后字典序较大者，保证两个方向收敛到同一结果
if (!localHasValue || stableValue(remoteValue) > stableValue(local[key])) { ...采纳远端... }
```

这样合并变成**可交换**的：无论谁先拉谁，最终都落到同一个值。不再有来回抄。

### 3. 合并后仍与远端不同 → 明确要求推送

`applyRemoteDoc` 的返回值新增：

```js
needPush: !isContentEqualToRemote(_getData(), doc, _status.docId),
```

调用方（初始化、周期同步、切回页面）看到 `needPush` 就推一次，让服务端收敛到合并结果。

## 一句话回答

是的，多标签让这件事更容易发生；但根因是**判「有没有变化」用版本号记账**、
**时钟打平时互相采纳**、**本地赢却不推** 这三件事。三处都改成「以内容为准 + 确定性收敛」之后，
配置不会再自己跳了。
