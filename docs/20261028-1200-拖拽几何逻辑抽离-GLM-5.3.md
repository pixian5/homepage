# 拖拽几何逻辑抽离（2026-10-28 12:00）

版本：26.3.7 → **26.3.8**。对应[复核与下一步开发方案](20261028-0832-复核与下一步开发方案-GLM-5.3.md)第 6 步的第一刀。

## 一、为什么只抽几何、不抽整个拖拽控制器

原计划是把「拖拽/触摸/右键菜单」整体搬成 `drag-controller.js`。读代码后发现**整体搬移风险过高**：

- `dragState`、`touchDragState`、`touchMenuState`、`openFolderId`、`activeGroupId` 等状态与 `app.js` 的 DOM 渲染、`data` 引用深度交织；
- 拖拽处理器直接调用 `render()`、`persistData()`、`moveNodeInList()`、`openContextMenu()` 等十余个 app.js 内部函数；
- 任何一处注入遗漏都会在**真实拖放时**才暴露（参考 26.1.5 设置面板拆分时漏注入 `SYNC_INTERVAL_OPTIONS` 导致 Safari 打开设置崩溃的先例）。

所以这轮先做**风险最低、收益明确**的一步：把纯几何判定抽出来，用测试锁住行为。剩下的事件绑定部分等有更完整的浏览器自动化后再动。

## 二、新增 `src/js/drag-geometry.js`

| 导出 | 作用 |
|---|---|
| `findNearestRect(rects, x, y)` | 在一组矩形中找距落点最近的一个（点到矩形距离） |
| `shouldInsertAfter(rect, x, y)` | 判断落点应插在目标「前」还是「后」 |
| `computeInsertIndex(list, targetId, rect, x, y)` | 组合上面两者算出插入索引（越界钳制） |
| `isPointInsideRect(rect, x, y)` | 点是否在矩形内（判断「拖到图标上」） |
| `toPlainRect(domRect)` | DOMRect → 纯数据对象 |

**`shouldInsertAfter` 的规则**（与原有实现逐条对齐）：

- 落在矩形左侧 → 前；右侧 → 后；
- 落在上方 → 前；下方 → 后；
- 落在内部：靠近纵向中心线（±35% 高度）时按左右半区，否则按上下半区。

`app.js` 的 `getDropIndex()` 与 `isDropOnIcon()` 改为调用这些纯函数，行为不变。

**注意**：`getInsertIndexFromTarget()`（文件夹内拖放）原本就是**纯左右半区**判断，与 `getDropIndex()` 的复杂规则不同。我保留了原语义，只在注释里写明差异——合并两者会改变真实拖放行为。

## 三、测试与验证

**单元测试**：`tests/drag-geometry.test.js`，**21 条**，覆盖：
- 最近矩形：内部命中、空隙取最近、空输入、null 输入；
- 前后判定：左/右/上/下、靠近中心线按左右、远离中心线按上下；
- 索引计算：未知目标钳制到末尾、目标元素缺失回退、越界钳制；
- 矩形内判定：四边外、边界算内、null；
- `toPlainRect` 字段拷贝。

**真实浏览器验证（Safari 26.3.8）**：用 `DataTransfer` 构造真实 `dragstart → dragover → drop → dragend` 事件序列，把第 1 张卡片拖到第 3 张的右半区：

```
拖拽前：[A, B, C, D]
拖拽后：[B, C, A, D]   ✅ A 正确插到 C 之后
```

行为与重构前一致。全量测试 **247/247**、Biome 82 文件零警告。

## 四、验证过程暴露的重要事实：Safari 数据有「两份」

拖拽测试写入了真实数据，还原时发现了此前不清楚的机制：

| 位置 | 作用 |
|---|---|
| `~/Library/Application Support/我的首页/homepage-data.json` | 宿主 App 侧的共享文件（崩溃恢复用） |
| `chrome.storage.local['homepage_data']` | **扩展运行时实际读取的数据源** |

**只改共享文件不起作用**——扩展启动时优先用自己 storage 里的副本，不会用文件覆盖。必须两侧一起改。

另外，文件夹内的顺序由**文件夹节点的 `children` 数组**决定，不是 `_syncMeta.placementClock`（后者只记录放置时钟用于同步合并）。这次还原时先改错了地方，浪费了一轮。

> 已把本轮测试造成的改动完整还原：`children` 顺序、`placementClock`、`lastUpdated` 与部署前备份逐项一致，45 节点无增减。**教训：真实数据上的交互测试，事前要记录、事后要双侧还原并逐项核对。**

## 五、下一步

拖拽控制器的剩余部分（事件绑定、触摸长按、右键菜单）仍留在 `app.js`。继续拆分的前提是先有**可自动化的拖放回归测试**（当前只能手工用 Safari 跑），否则每次搬移都要人工验证，成本高于收益。建议优先级下调，先做设备退役与生产回收演练。
